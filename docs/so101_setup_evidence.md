### H8: translation axes may differ

The native three-view pose runs move substantially away from soup; unchanged *minimum* target distance does not mean a stationary robot. Left/right measured TCP XYZ spans are 15.9/30.7/15.1 cm and 17.0/18.2/7.7 cm. Released `robotwin_icl.json` has forward-looking Y quantiles ≈0–0.39 m while this scene's reachable workspace is along +X. This suggests an axis mismatch, but quantiles alone do not prove it. `evaluation/robotwin/eval_policy_client_openpi.py:add_eef_pose` adds translations in world axes and composes relative quaternions with the initial TCP orientation. New `pose_three_{left,right}_native_yawneg90` variants rotate model translation −90° about Z (+Y→+X), inverse-rotate measured translation for history, and preserve the initial-relative quaternion (invariant to a global coordinate-frame rotation). Tests pending; this is a controlled adapter hypothesis, not a claimed robot convention.

### H14: native action reference is a virtual wrist, not SO-101 TCP

**Confirmed setup mismatch:** `/workspace/Robotwin/envs/_base_task.py:get_arm_pose` calls `get_*_ee_pose`, not `get_*_tcp_pose`. In `envs/robot/robot.py:_trans_endpose`, EEF translation uses `gripper_bias−0.12`; TCP uses `gripper_bias`. Aloha `assets/embodiments/aloha-agilex/config.yml` sets bias 0.12, so the model acts at the wrist reference, **12 cm behind the grasp center along reported tool +X**. Its `robot_pose` faces +Y, confirming the earlier translation-axis hypothesis. SO-101 `so101.xml:gripperframe` explicitly defines **local +Z toward fingertips** at the grasp center. Native gripper separation is along reported Y; SO-101 jaw separation is along TCP X (checked in loaded geometry).

`zero_wam/so101_actions.py:{robotwin_to_tcp_relative,tcp_to_robotwin_relative}` now conjugate relative orientation through the proper tool basis (native X→TCP Z, native Y→TCP X, native Z→TCP Y), and add/remove the rotating 12 cm lever arm. Model translation is still yaw-converted −90°. Measured feedback inverse-converts the actual TCP to the same virtual-wrist convention; target-to-realized errors use the converted physical target. **100 randomized forward/inverse round trips passed.** `pose_robotwin_tool_{left,right}` combine this with native 16-channel mask, released stats, three camera streams, and task-facing high view. Prior pose screens are evidence about incomplete adapters, not proof of model inability. This exact native wrist convention is verified for RoboTwin; it is not claimed for every pretraining dataset.

### H15: reproduce the native client's quaternion algebra

`Robotwin/envs/robot/robot.py:_trans_endpose` returns `transforms3d.mat2quat` (absolute **WXYZ**). The shipped `eval_policy_client_openpi.py:add_eef_pose` feeds that raw array into SciPy's **XYZW** API, composes the predicted relative quaternion, then sends the resulting four numbers to RoboTwin as absolute WXYZ. Thus the model's relative four-vector is not automatically the standard physical initial-relative quaternion assumed by H14. Training-data export order remains unverified; native inference behavior is directly verified from code.

`quaternion_convention="native_client"` in the two conversion helpers explicitly reproduces that end-to-end native client convention in the rotated world/tool frame, with the inverse applied to measured feedback. Separate `pose_robotwin_client_{left,right}` variants retain the standard physical-quaternion variants as controls. **300 randomized cases** across world yaw −90/0/+90 match the *actual shipped* `add_eef_pose` function and round-trip through measured feedback (`outputs/zero_wam/so101/pose_convention_checks.json`). A mathematical round trip alone was insufficient; comparing against the native client revealed this difference.
